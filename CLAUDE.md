# CLAUDE.md

Guidance for Claude Code (claude.ai/code) in this repo.

## What this is

`comparebuilds` (comparebuilds.app): a WoW talent-build comparison tool. React 19 + Vite + Tailwind v4 SPA. Users paste the game's native talent loadout strings; app decodes them and renders trees side-by-side (diff for 2 builds, adoption heatmap for 3+), plus an interactive calculator. Sharing is backed by a small PHP + MariaDB short-link API. No runtime backend for the app itself — static files plus that one share endpoint.

## Commands

```bash
npm run dev          # Vite dev server (PHP API is NOT available locally — share links 404 locally)
npm run build        # produce static site in dist/ (also prerenders spec landing pages, sitemap, robots.txt, and api/current_layouts.json)
npm run lint         # ESLint (flat config)
npm run format       # Prettier write across the repo (format:check verifies; used by CI)
npm test             # run all Vitest suites once
npm run test:watch   # watch mode
npm run coverage     # run with coverage; FAILS below the thresholds in vite.config.js
npm run check:csp    # verify inline script hashes match BOTH CSPs (built <meta> baseline + dist/.htaccess header) and the two policies agree (runs against built dist/)
npm run check:og     # verify public/og-image.png matches the og:image metas index.html advertises
npm run check:shared # the mirrored tools/shared/ bundle matches MANIFEST.sha256
npm run shared:hash  # regenerate that manifest after an intended bundle edit
npm run test:shared  # the bundle's stdlib-only tests (node --test; vitest cannot collect them)
./validate.sh        # run the FULL gate locally: shell, php, lint, format, css/md/svg, tests, build, CSP, OG, sitemap (--clean runs npm ci first)
npx vitest run src/lib/buildString.test.js   # run a single test file
npx vitest run -t "round-trip"               # run tests matching a name
node scripts/ingestBlizzard.js               # verify the data (Game Data API + client DB2) against the snapshot (writes nothing); --promote to write src/data/; --no-descriptions / --no-icons to skip the soft fetches. Needs API credentials — see .env.example
node scripts/compareSources.js               # re-derive from Blizzard live and diff vs committed data — the drift/freshness check (hard = build-string fields, soft = presentational)
node scripts/checkWireLayout.js              # confirm the build-string node order against Raidbots talents.json; no credentials, --env=ptr/beta checks a test channel
node scripts/checkGameBuild.js               # has the game moved past the build in scripts/gameBuild.json? cheap credential-free probe; --exact also flags hotfix builds, --accept records a new one
node scripts/fetchTopBuilds.js               # regenerate src/data/topBuilds.json from Raidbots' top-sims summary (dry run; --write to commit the change)
node scripts/fetchIcons.js                   # download referenced icons (Blizzard render CDN) into public/talent-icons/ (incremental; commit the result)
UPDATE_SNAPSHOTS=1 npm test                  # deliberately rewrite wireLayout snapshots (see below)
```

CI is the `validate` job in `.github/workflows/deploy.yml`, on every push/PR: ESLint, Prettier, stylelint (CSS), markdownlint, svgo (SVG), `php -l` + php-cs-fixer + PHPUnit (share API + OG renderer), shfmt + shellcheck, actionlint, then `npm run coverage` (enforcing thresholds) and `npm run build`, then these guards:

- **CSP guard** (`npm run check:csp` → `tools/check-csp.mjs`). The CSP is declared twice: a `<meta>` baseline injected into the built HTML by `cspMetaPlugin` in `vite.config.js` (the `vite preview` twin — build-time only, so the dev server's inline HMR scripts aren't blocked) and the `dist/.htaccess` header superset (adds `frame-ancestors`/`upgrade-insecure-requests`, which a `<meta>` CSP can't express). The guard recomputes the sha256 of every inline `<script>` in built `dist/index.html` and fails if a token is missing from the **`script-src`** of **either** policy (so the anti-flash theme script's hash can't drift from the allowlisting policies), and fails if the two policies disagree on any other directive (catching a loosening applied to only one). The header-only pair is pinned to its expected value, not merely checked for presence, so `frame-ancestors 'none'` can't be weakened to `frame-ancestors *` and still pass. Every parsing rule it needs lives in a `tools/` helper with a test of its own — all five of them in the mirrored `tools/shared/` bundle (see below): `shared/html-comments.mjs`, `shared/html-tags.mjs` (quote-aware tag/attribute scanning), `shared/inline-scripts.mjs`, `shared/csp-directives.mjs` (first-wins directive parsing, the two-policy comparison) and `shared/htaccess-csp.mjs` (Apache line continuations, comments, request scopes, **last-wins** over repeated headers, and refusing the `append`/`edit`/conditional forms that serve something other than the value read). That split is the rule, not a one-off: a guard regex that is subtly wrong on real input fails in the fail-open direction, so when a guard needs to read something new, add it as a tested helper — never a private regex inside the guard.
- **Deploy set guard** (`npm run check:deploy-assets` → `tools/check-deploy-assets.mjs`): binds `deploy.sh`'s `API_ASSETS` array to the tracked `api/` tree. Every tracked `api/` file must be classified as shipped or explicitly withheld, every array entry must resolve to a tracked (or declared build-generated) path, and every `__DIR__`-relative require reachable from a shipped PHP file must itself be staged or resolve above the web root (where `config.php` lives). Since `deploy.sh` stages `api/` with `git archive` the entries are git **pathspecs**, so the guard also refuses glob/pathspec magic (the prefix matching it does here would then stop meaning what the deploy does) and binds `API_GENERATED` — the gitignored, build-written subset staged from disk instead — requiring each of those to be listed in `API_ASSETS` and to be genuinely untracked. Require scanning is in `tools/php-requires.mjs`, the array parsing in `tools/shell-arrays.mjs`, both tested. Runs after the build, since the array names the generated `api/current_layouts.json`.
- **OG image guard** (`npm run check:og` → `tools/check-og-image.mjs`): reads the PNG IHDR and fails if `public/og-image.png` isn't the size `index.html`'s `og:image:width`/`og:image:height` metas advertise. The expected size is read from the metas, not restated in the guard, so the two can't drift apart — and `tools/ogDimensions.test.js` does the same for the dynamic card, binding `api/share.php`'s emitted metas to `api/og.php`'s `$W`/`$H`.
- **sitemap check** (`xmllint --noout dist/sitemap.xml`): freshly built sitemap must be well-formed XML.
- **HTML validation** (Nu Html Checker over `dist/` — entry page, every prerendered spec landing page, SVG favicon; needs a JVM, so CI sets up Java 21 + downloads `vnu.jar`). Two `file://`-only infos are filtered (void-element trailing slash, Vite/Prettier house style; and the meta-CSP resolve failure, where `script-src 'self'` + inline-hash allowlist can't resolve without an origin). Generated Tailwind CSS is deliberately not checked (vnu rejects modern properties).

The `deploy` job `needs: validate`, so a red gate never ships (deploy skipped on PRs). After a successful deploy, `deploy.sh` runs `api/cron/ensure_schema.php` over SSH to apply pending schema migrations. `./validate.sh` mirrors the gate locally — shellcheck, shfmt, php-cs-fixer, phpunit and actionlint are downloaded at their `.tool-versions` pin into a gitignored `.tools/` cache, exactly as CI does, so a `brew upgrade` can't drift a tool out from under its pin; an unavailable download falls back to the still-version-asserted PATH copy. CI keeps the same five in the same `.tools/` paths behind an `actions/cache` keyed on `.tool-versions`, so a routine run fetches none of them — a release host being down reddened the gate on good code before that. CI takes shellcheck from there too rather than from the runner image, so an image bump can't move it under a pin every other tool honours. `vnu.jar` is deliberately left uncached: it is pulled from the mutable `latest` tag, and caching it would silently pin the validator to whichever build a cache entry happened to capture. The CLIs with no pinned download (xmllint, vnu) are skipped with a notice when absent; shellcheck and shfmt are resolved and skipped independently of each other, so a machine missing one still runs the other; npm tools always run.

Non-gating workflows, kept out of the gate deliberately: link checking (lychee, `links.yml`) so a dead link never blocks a release — that workflow also runs `npm run check:security-txt` (`tools/check-security-txt-expiry.mjs`), which fails once `public/.well-known/security.txt` passes its `Expires` (an expired RFC 9116 file is invalid, so the contact stops being published) and warns for the 60 days before. It lives here rather than in the gate for the same reason `npm audit` does: it fails on the calendar, not on a change, and a self-imposed date must not redden a green tree on a day nobody touched the security contact. The half that IS edit-driven — the contacts matching `SECURITY.md`, the `Canonical` matching `index.html`'s, the required fields being present — stays in the gate as `src/lib/securityTxtParity.test.js`. Bumping the date is a human acknowledgement like `scripts/gameBuild.json`'s stamp: re-confirm the contacts, then set a new one. PHP static analysis (Semgrep, `semgrep.yml`) uploading SARIF to GitHub code scanning (Security tab) to cover `api/*.php` that CodeQL's default setup can't (no PHP support) — like CodeQL, never fails on findings, an alert is a triage signal not a blocked deploy; dependency advisories (`npm audit`, `audit.yml`), which splits the tree the way `sources.yml` splits divergences — **runtime** dependencies are hard (bundled and served, so any severity fails the job), **dev** dependencies are soft (build and test tooling that never reaches the browser, reported via `continue-on-error`). `npm audit` is deliberately absent from `validate.sh` and the `validate` job: an advisory published upstream on someone else's schedule must not be able to redden a green tree and block an unrelated deploy. Dependabot still opens the fixing PR; this adds a check on the PR that introduces a dependency and a result visible in the Actions tab. It also runs `scripts/checkStaleOverrides.js`, which re-resolves and audits the tree with each `overrides` entry removed in turn: an override is a fix with no natural end, and a clean audit without one means upstream has caught up and the pin is now just holding a package back.

Coverage is gated only over `src/lib/**` and `src/store/**` — keep logic there, keep components thin. Thresholds in `vite.config.js` are a ratchet: raise as coverage climbs, never lower. `treeLogic.js` has a per-file 100% threshold — the prereq/gate cascade is the correctness core.

## Architecture

**Data is the contract.** The app reads ONLY the normalised JSON in `src/data/*.json` (one file per class, plus `classes.json` as the index). It never talks to any external source at runtime. How that JSON is produced is an implementation detail behind the schema enforced by `src/lib/validateClassData.js`. When swapping or repopulating data, the only requirement is the output matches that schema; the validator and round-trip tests confirm it.

**One source: Blizzard.** `scripts/ingestBlizzard.js` is the sole ingest, mapping Blizzard's data to the schema and handing off to the shared pipeline `scripts/lib/ingestCore.js` (validate → write `src/data/` → regenerate the snapshot). It reads Blizzard's **Game Data API** for tree structure, and the client's **DB2** tables (via wago.tools, `scripts/lib/blizzardDb2.js`) for what the web API doesn't expose cleanly — the spec **apex** capstone's true rank chain (distinct per-level spells, ranks, unlock levels), the authoritative per-node points gate (`spentRequired`), and hero-subtree descriptions. Needs Battle.net API credentials (build-time only; see `.env.example` and `scripts/lib/blizzardApi.js`). `--promote` writes `src/data/`; add `--update-snapshot` only to deliberately redefine the build-string oracle. (History: Icy Veins and Wowhead were earlier sources, removed once Blizzard + DB2 replaced them. The pipeline stays source-agnostic.)

`scripts/compareSources.js` is the drift/freshness check: re-derives from Blizzard live and diffs against committed `src/data/`, separating **hard** divergences (wire layout, ranks, choice arity, gates, prereqs — must agree) from **soft** (positions, names, descriptions, per-spec membership). Runs in the non-gating `sources.yml` workflow (network + API secrets, kept out of the gate). A red run means committed data has drifted from a new game patch (or a bad hand-edit) — investigate, not a blocked release. NB: Blizzard's tree layout is the game's own grid, so the data uses it directly (positions soft); the renderer normalises per panel, and `display_col` is doubled to the step-2 spacing the renderer expects so choice nodes don't overlap.

`scripts/checkWireLayout.js` is the narrower companion check, and the only upstream check that runs on fork PRs. It compares just the build-string node ordering against Raidbots' published `talents.json` — an **independent derivation of the same client** (SimC casc/dbc tools), so it is outside evidence rather than the self-comparison the committed snapshot performs. No credentials (plain public GET, cached under `scripts/.cache/raidbots/<env>/<contentHash>/` — keyed by content hash so a new upload can't be served from a stale entry, which would be a false green), and `--env=ptr`/`--env=beta` read a test channel's node set, so a break surfaces before it ships **when that channel is ahead** — it is not always: between patches a channel can sit on an older build than live (each channel's `metadata.json` reports its `wowBuild`), where a divergence means nothing. `live` mismatch → exit non-zero; `ptr`/`beta` mismatch → warn only, and an unpublished test channel (404) is a no-op. Runs in `sources.yml` as the `wire-layout` job.

`scripts/checkGameBuild.js` is the cheap probe that decides whether the other two are worth running: it reads the `wowBuild` in each channel's `metadata.json` (~1 KB, no credentials) and compares **live** against the acknowledgement stamp in `scripts/gameBuild.json`. It compares the **patch version** by default, not the whole build string — talent trees change with a patch, while the build number moves for every hotfix, so comparing whole strings would produce constant meaningless alerts (`--exact` opts back in). The stamp is a human acknowledgement, not a derived fact (nothing in `src/data/` records its build): update it with `--accept` **after** re-ingesting or confirming a patch changed nothing, never to silence the check. Reporting all three channels is also how a `checkWireLayout` warning on ptr/beta becomes readable — it says whether that channel is ahead of live or stale. In `sources.yml` it runs in the `upstream` job on a **daily** cron; the credentialed `compare` job opts out of that cron and stays weekly.

`scripts/fetchTopBuilds.js` generates `src/data/topBuilds.json` from Raidbots' daily top-sims CSV. Its `talents` column is a raw Blizzard loadout string, so it decodes with our own parser — **every** shipped string is decoded against committed class data before it is written, and a >10% drop rate fails the run (the app loads these directly, so an undecodable one is a broken slot). Pooling across fight styles or target counts is refused: an AoE and a single-target build listed together would read as alternatives to the same question. The file IS committed, keeping the "no external source at runtime" rule intact, and `src/data/topBuilds.json` is excluded from `storeHelpers.js`'s class-data glob so it doesn't become a phantom class chunk. `fetchTopBuilds.test.js` re-decodes the whole committed table, which incidentally makes it a second wire-layout check: a data change that shifts bit positions stops these real strings parsing. The table is refreshed by the **weekly** `top-builds` job in `sources.yml`, which regenerates it and opens a PR (one reusable branch, force-pushed) when the content actually moves — weekly because the upstream sample is a rolling 30-day window whose counts drift daily while the builds it recommends don't, and the script leaves the file untouched when only `generatedAt` would change, so a no-op refresh never opens a PR. That job is the only thing in this repo that writes, and it does so with `TOP_BUILDS_PAT` — a fine-grained PAT scoped to this repo (`contents: write`, `pull requests: write`) — rather than `GITHUB_TOKEN`, whose route to opening a PR needs the repo-wide "Allow GitHub Actions to create and approve pull requests" toggle that would also grant every workflow here PR-**approval** power. The job's own `GITHUB_TOKEN` is therefore `contents: read`, the checkout is done with the PAT so the force-push carries its identity, and a missing secret fails the job on a guard step before any work. Because the PAT's identity does trigger workflows, `validate` runs on the PR it opens — a `GITHUB_TOKEN` push raises the event as `github-actions[bot]`, and GitHub parks bot-actored runs at `action_required`, awaiting an approval that never comes; the in-job decode test stays as the fast fail, before a branch is pushed over an undecodable table. Skipped on `pull_request` so a fork PR never runs with the PAT in scope.

**The three layers:**

- `src/lib/` — pure logic, no DOM, unit-tested in Node. Where correctness lives:
  - `buildString.js` — decode/encode the game's binary talent loadout string (LSB-first base64 bit-packing; format documented in the file header). `collectClassNodes()` builds the class-wide, ascending-sorted node list the parser walks — node bit-positions depend on this exact ordering. Wire format is fixed by the game and version-locked (`SERIALIZATION_VERSION = 2`); parsers reject other versions loudly. `bitStream.js` is the underlying bit reader/writer.
  - `treeLogic.js` — prerequisite + gate-threshold cascade (`computeInvalidNodeIds`, `hasUpperPrereq`, `gatedPoints`). Shared by interactive and import views so they can't drift. Also resolves which hero subtree a build committed to (`selectedHeroSubtree`) and drops the other (`pruneInactiveHeroNodes`): **the game stores talent choices in BOTH hero subtrees and exports both**, so a player who has filled their second tree exports two complete subtrees and only the gate node says which is live. The gate is consulted solely to break that tie — one spent subtree wins over a contradicting gate, because Wowhead writes a gate naming the subtree it did not invest in, and believing it would prune away the build's only hero talents.
  - `spendRules.js` — interactive calculator's "can I spend a point here" rules (section budgets, hero-subtree exclusivity, gates, prereqs).
  - `diff.js` / `heatmap.js` — pure comparison + adoption-counting logic, extracted from their components for testing. Also classify what counts as a "difference" for the changes-only filter (`diff.js` per-node highlights; `heatmap.js` `isContested`/`isDivergent`, where a heatmap "change" is split adoption or a choice node whose picks diverge).
  - `validateClassData.js`, `wireLayout.js`, `sanitizeDescription.js` — schema validation, wire-layout fingerprinting, HTML sanitisation at ingest.
  - `exportBuild.js` — generates a valid build string from an interactive selection (prunes inactive hero subtrees, injects hero gate selection). The read-side mirror lives in `parseAll` (`storeHelpers.js`), which prunes on import so every view sees one subtree; keep the two rules in step.
  - `buildLabel.js` — default human-readable label for a build slot.
  - `simcProfile.js` — SimulationCraft profileset block from the active comparison slots.
  - `prereqChain.js` — hover-highlight helper: node ids directly relevant to a hovered node (itself, direct prerequisites, direct dependents).
  - `route.js` — entry-route resolution: from the URL, load a server share, a prerendered spec page, or restore from local storage.
  - `shareLink.js` — POSTs build data to the share API, returns the short-link ID.
  - `safeStorage.js` — safe storage abstraction for Zustand persistence where Web Storage is unavailable.
  - `talentSearch.js` — matcher for the search box: node ids whose name/description contains the query.
  - `topBuilds.js` — reference builds from Raidbots' public top-sims summary (generated into `src/data/topBuilds.json` by `scripts/fetchTopBuilds.js`, lazily imported so a session that never opens the feature never downloads it). Entries are ranked by how many of the top sims repeated the same talent string, **not** by dps — dps isn't comparable across rows with different gear. Mind the framing: most rows are Raidbots' optimiser output on a single target, so this is "what sims well", not "what the community plays", and being DPS-sim data it covers no healing specs at all — an empty spec is an ordinary case, never an error.
  - `theme.js` — pure three-way theme-cycle helpers (auto/light/dark), no DOM. Parity with acurioustale.
  - `iconUrl.js` — builds the first-party icon URL (`/talent-icons/…`).
- `src/store/` — single Zustand store; the app's state machine. `buildsStore.js` is the entry point, composed of slices (`slices/buildsSlice.js`, `slices/interactiveSlice.js`). Holds raw build strings, their parsed results (kept parallel — `null` = not-yet-parsed or failed), loaded `treeData`/`classNodes`, and interactive selections. Class JSON is dynamically imported per-class (lazy Vite chunks via `import.meta.glob` in `storeHelpers.js`). A module-level `loadGen` counter (`slices/loadTreeData.js`) cancels stale async loads on reset/spec-switch. `MAX_BUILDS`/`MAX_BUILD_LEN`/`MAX_BUILD_NAME_LEN` in `slices/constants.js` are mirrored server-side in `api/share.php` (`MAX_BUILDS`, `MAX_BUILD_LEN`, `MAX_LABEL_LEN`) — keep them in sync.
- `src/hooks/` — React hooks: share rehydration (`useShareRehydration.js`), share actions (`useShareActions.js`), theme (`useTheme.jsx`).
- `src/components/` — thin React renderers. `App.jsx`/`MainView` picks the view by valid-build count: 0 → `InteractiveTalentTree`, 1 → `TalentTree`, 2 → `SideBySideDiff`, 3+ → `HeatmapTree`. `treeLayout.js` holds shared geometry constants so `TalentTree` and `HeatmapTree` can't diverge. `FitToWidth.jsx` scales each panel to viewport width via a uniform CSS transform (scale, don't reflow). The search box (`TalentSearch.jsx`) and the "changes only" toggle (dims nodes builds agree on) are both wired in `MainView` and drive every node through one `useNodeEmphasis` hook (`SearchContext.js`), so diff and heatmap renderers can't dim differently. `SearchContext.js` exports three contexts: `SearchContext` (query match), `ChangesFilterContext` (changes-only toggle), `SpotlightContext` (a single node id dimming everything else — driven by `DiffSummaryTable` hover-to-spotlight). `TalentNode.jsx` is the shared node renderer for every tree view. `Tooltip.jsx` wraps Floating UI for themed hover/click tooltips. `DiffSummaryTable.jsx` renders a tabular summary of talent differences; hovering a row spotlights that node via `SpotlightContext`. `BuildManager.jsx`/`BuildManagerSlots.jsx` manage the build input slots. `useBuildExport.js` and `useTapGesture.js` are local hooks for the interactive tree's export UX and touch gestures. Icons are served first-party from `/talent-icons` (URL built by `lib/iconUrl.js`), downloaded from Blizzard's render CDN by `scripts/fetchIcons.js` and committed under `public/talent-icons/`, because hotlinking the CDN got images blocked by content blockers and tracking protection. (Path is `/talent-icons`, not `/icons`, because Apache reserves `/icons` for mod_autoindex's directory-listing graphics — that alias shadows a web-root `icons/` folder.)

Routing is hash-based (an 8–16 char content-addressed share id in the URL hash); the SPA's own routes are all served by `index.html`. The one server-side rewrite (`public/.htaccess`) is unrelated to SPA routing: it maps pretty share URLs `/s/<id>` to `api/share.php` for link-unfurl previews.

## The wire-layout snapshot — read before editing `src/data/`

`src/lib/wireLayout.snapshot.json` fingerprints each class's build-string bit layout. After any data change, run `npm test`:

- A **schema** failure (`dataIntegrity.test.js` / `validateClassData`) means the file is structurally wrong — fix it.
- A **wire-layout snapshot** failure means your change shifted build-string bit positions, so **every existing build string and share link for that class now parses differently**. Only if intentional (e.g. a new game patch added nodes) regenerate deliberately with `UPDATE_SNAPSHOTS=1 npm test`. `scripts/ingestBlizzard.js --promote --update-snapshot` regenerates the snapshot too — merging the promoted classes' fingerprints into the existing file — and aborts without updating it if any class fails validation; `--promote` alone writes `src/data/` but leaves the snapshot untouched.

Key data-correctness tests: `buildString.test.js` (per-class encode→decode round-trips), `buildFixtures.test.js` (decodes real in-game-exported strings to confirm node IDs/ordering/budgets — every spec fixture must come from the game's own copy-talent-string button; third-party calculator strings are weaker evidence and belong only in the labelled tool-built cases, never as a spec's fixture), `dataIntegrity.test.js` (schema + snapshot), `treeLogic.test.js` (prereq/gate cascade). Cross-stack parity tests keep JS and PHP mirrors from drifting: `limitsParity.test.js` pins `MAX_BUILDS`/`MAX_BUILD_LEN`/`MAX_BUILD_NAME_LEN` against `api/share.php`; `shareIdParity.test.js` pins the share-id regex in `route.js` against `share.php` and `og.php`.

## Vitest environment convention

Tests default to the `node` environment. Component suites needing a DOM opt in per-file with a `// @vitest-environment jsdom` pragma at the top (`src/test/setup.js` is the shared setup).

## The mirrored `tools/shared/` bundle

Five of the CSP guard's parsing helpers — `html-tags.mjs`, `html-comments.mjs`, `inline-scripts.mjs`, `csp-directives.mjs`, `htaccess-csp.mjs` — live in `tools/shared/` and are duplicated **byte-for-byte** in the sibling repo [acurioustale/acurioustale-de](https://github.com/acurioustale/acurioustale-de). Both repos validate the same kind of markup and the same `.htaccess` CSP with the same guards, and neither wants a private copy of a regex that has already been got wrong once. This is deliberately not a package: no publish step, no version to bump, no dependency to add — a vendored bundle plus an alarm.

What may go in follows from that constraint. Everything in the bundle — helpers and tests alike — depends on the Node standard library and nothing else: `node:test` and `node:assert/strict`, no test framework. The two repos do not run the same test runner, so a file reaching for one stops being mirrorable the moment it is written. A helper that needs more than the stdlib does not belong here; keep it in `tools/` on this side and let the other repo have its own.

The bundle's own tests live in `tools/shared/` beside the helpers, not with the rest of ours. That is the only exception to where our tests go, and it follows from the same constraint: the bundle must be byte-identical across two repos that place their tests differently, so a test importing `../tools/shared/html-tags.mjs` could not be. Beside the helper, `./html-tags.mjs` resolves in both. The cost is one config change — **vitest cannot collect a `node:test` file**: it reports "No test suite found in file …" and fails the suite, while Node's own runner executes the assertions where vitest cannot see them. So `vite.config.js` excludes `tools/shared/**/*.test.js` from the vitest include, and `npm run test:shared` (`node --test tools/shared/`) runs them from `validate.sh` and the `validate` job instead. The other `tools/` tests (`ogDimensions`, `phpRequires`, `securityTxt`, `shellArrays`) are unaffected and still run under vitest. Do not "fix" this by converting the bundle's tests to vitest — that is exactly what makes it unmirrorable.

Coverage is asymmetric on purpose. Here `coverage.include` is `src/lib/**` and `src/store/**` only, so `tools/` is outside the gated surface — but these same five helpers are gated at 100% in the sibling, so their coverage is enforced from that side alone.

Two alarms watch the bundle, because one repo's gate cannot see the other:

- **Locally, on the gate.** `tools/shared/MANIFEST.sha256` pins every file in the bundle (`<sha256>  <filename>`, sorted), and `npm run check:shared` (`tools/check-shared.mjs`, run from `validate.sh` and `deploy.yml`) fails if the set of files or any hash differs. So editing a shared helper without consciously re-hashing breaks the gate, and the failure message is where you are told to mirror the change. Regenerate with `npm run shared:hash` after an intended edit; it is a no-op on a clean tree.
- **Across repos, weekly.** `.github/workflows/shared-sync.yml` shallow-sparse-clones the sibling's `tools/shared/` and diffs the two bundles, on a Monday 09:00 UTC cron, on `workflow_dispatch`, and on any push to `main` that touches the bundle. **Non-gating**, like `links`, `audit`, `sources`, `semgrep` and `e2e`: a sibling that has not yet mirrored a change must never block a release here, so a red run is a signal to go mirror it, not a blocked deploy. The clone is unauthenticated, because both repos are public; it is never gated on a credential existing, since that would leave the job skipping green against a repo it can already read — precisely the quiet failure the workflow exists to prevent. Should either repo go private, a fine-grained read-only PAT in a `SHARED_SYNC_TOKEN` secret is picked up automatically: the clone is attempted either way, a failure without a token reports what is missing, and a failure with one set is a hard error rather than a skip.

The rule the whole arrangement exists to enforce: **a fix to any shared helper has to land in BOTH repos.** The manifest makes you notice you touched one; the weekly diff makes you notice you only did it once.

## Deployment

Pushes to `main` auto-deploy via GitHub Actions: the `deploy` job runs only after the `validate` gate passes (`needs: validate`), so a red push never ships. `deploy.sh` stages `dist/` together with the PHP API (`api/share.php`, `api/og.php`, `api/lib/`, `api/fonts/`, `api/cron/`, `api/current_layouts.json`) into one tree and mirrors it with a single `rsync -avz --delete` to the web root; after a successful rsync it runs `api/cron/ensure_schema.php` over SSH to apply pending schema migrations **and** reconcile the layout-history table from `api/current_layouts.json` (build-generated manifest of currently-valid layout hashes — see retention note below).

`dist/` is copied off disk (a build product, untracked); `api/` is extracted from **HEAD** with `git archive`, so a hand-run `./deploy.sh` from a dirty checkout cannot publish uncommitted PHP to the internet-facing half (it prints a note instead). The gitignored `api/current_layouts.json` is the exception, staged from disk via `API_GENERATED` — a gitignored path handed to `git archive` matches nothing and aborts the archive.

The staged list MUST include every runtime dependency of the API — `api/lib/` holds `RateLimiter.php`, which `share.php` requires; `api/current_layouts.json` lets the prune job tell superseded layouts from current. Omitting either makes `rsync --delete` remove it server-side and either fatal every share/OG request or silently break supersession-gated pruning. That list is the `API_ASSETS` array in `deploy.sh`, and the deploy set guard above enforces the invariant — keep it a single one-line array literal, which is what the guard parses.

The deploy key is confined server-side by a forced-command rsync jail; reviewed source tracked at `ops/rsync-jail-comparebuilds.sh` (manually installed to `~/bin/` on the host — the server copy is authoritative). The jail allow-lists exactly the SSH commands `deploy.sh` issues (the rsync push and the `ensure_schema.php` migration), so a new `ssh` call in `deploy.sh` needs a matching jail entry and a reinstall, or the deploy fails with `rsync-jail: only rsync push allowed`. Manual/local path: `npm run build` → `./deploy.sh` (or `--dry-run` to preview).

`config.php` (MariaDB credentials, `SHARE_IP_SALT`, optional `REDIS_HOST`/`REDIS_PORT`, proxy trust flags) lives one level **above** the web root so it stays private if PHP processing fails.

Schema DDL — `CREATE TABLE IF NOT EXISTS` for every table plus additive `ADD COLUMN`/`ADD INDEX IF NOT EXISTS` retention migrations — lives in `ensure_share_schema` in `share.php`, but is invoked **only** by the deploy-time `api/cron/ensure_schema.php` migration (CLI-guarded, run over SSH); live `share.php` requests never issue DDL. `get_db_connection` keeps schema creation separate so endpoints don't pay a DDL round-trip or take metadata locks on the hot path.

Pruning is **supersession-gated**, not flat-age: a `GET` touches the row's `last_accessed` (debounced to one write/day; response cached `immutable`, so it only fires on a cold-cache open) and each share stamps its `layout_hash`; the daily cron `api/cron/prune_shares.php` deletes a share only once its layout is no longer current **and** the link has been unaccessed for 180 days **and** that layout was superseded ≥180 days ago (so the idle window is entirely post-supersession) — a live-layout or recently-opened link is never pruned; legacy rows with no `layout_hash` age out on the unaccessed clock alone. `ensure_schema.php` maintains the `comparebuilds_layout_history` table (which hash is live vs. when superseded) by reconciling against `api/current_layouts.json` on every deploy; an empty/missing manifest is a no-op so a broken build can never mass-supersede.

`og.php` renders the Open Graph preview image for shared links (needs PHP GD with FreeType; ships its own bold TTF in `api/fonts/`); it caches rendered images in `cache_og/` one level **above** the web root (beside `config.php`, resolved as `../../cache_og` from `api/`) so `rsync --delete` can't wipe the cache each deploy and `prune_shares.php` cleans the same directory `og.php` writes.

Full steps, server layout, and the share-link API contract/limits are in `README.md`. The API is hardened for public exposure (per-IP rate limit via database or optional Redis, fail-fast GET_LOCK timeout, strict CSP, body cap, strict validation, same-origin only, prepared statements, explicit proxy trust flags) — preserve those properties when touching `share.php`. Its input validation lives in pure, PHPUnit-covered helpers (`validate_share_input` / `valid_share_id`, tests in `tests/`); request dispatch is guarded behind `SHARE_API_NO_MAIN` so those helpers can be included and tested without a database. The PHP test suite (`tests/`) covers share validation, concurrency, OG rendering, and supersession-retention helpers (`OgRenderTest.php`, `ShareConcurrencyTest.php`, `ShareValidationTest.php`, `LayoutRetentionTest.php`). PHP is held to PSR-12 by php-cs-fixer.

## Memory

Facts not cheaply greppable and not covered above. (`GEMINI.md` and `AGENTS.md` symlink to this file — one memory serves Claude Code, Gemini CLI, and AGENTS.md-standard tools like opencode.)

- **Toolchain is pinned in `.tool-versions`** (asdf/mise format): an exact nodejs release, php 8.4, plus shellcheck/shfmt/php-cs-fixer/phpunit/actionlint versions. mise reads that file but must not supply all of it, so `.mise.toml` disables three entries: the php-cs-fixer and phpunit **phars** (not in its registry — `validate.sh` and CI fetch them into `.tools/`) and **php** itself (Homebrew's keg-only `php@8.4`; left enabled, a bare `mise install` tries to compile PHP from source). What mise is left managing is node, shellcheck, shfmt and actionlint — and of those only node matters, since nothing else installs the pinned engine for you. The node pin names a full `major.minor.patch` on purpose — `setup-node` installs exactly what it reads, so a bare major would have CI follow whatever the newest release of that major happened to be that week, and "the same Node as CI" would mean a different engine week to week. CI reads it via `setup-node`'s `node-version-file`; match it when reproducing CI locally. Node is the one pin `validate.sh` can't fetch for you, so a wrong **major** blocks the run while a minor/patch difference only warns. `npm` (package-lock.json) — CI installs with `npm ci`. The **php pin tracks the production server, not the newest release** (8.4 is the latest it supports), so never bump it to chase a new PHP — `validate.sh` enforces an exact major.minor match. It stops at the minor while the node pin names a patch, and that asymmetry is deliberate: the two answer to different authorities. Node's pin exists so CI and local run the same engine as each other, and both sides can honour it exactly (`setup-node` and `mise install` each install the version they read). The php pin exists to match the **host's** minor, which is the actual compatibility contract; nobody controls its patch, and the server does not advertise it. Pinning a patch would not bring CI closer to production, only to a number we chose — and nothing could satisfy it locally anyway, since brew's `php@8.4` is whatever patch is current and mise's only route is the source build `.mise.toml` disables. Don't "fix" this by pinning a patch. On macOS `php@8.4` is keg-only, so a linked `php` 8.5 shadows it and `validate.sh` aborts before running anything; put `/opt/homebrew/opt/php@8.4/bin` first on `PATH`. That runtime pin is the one brew can still break: the pinned _tools_ are fetched, not taken from brew, so only the PHP engine itself has to be right locally.
- **`sanitizeDescription.js` is build-time only, despite living in `src/lib/`.** Its only caller is `scripts/ingestBlizzard.js`, so `dompurify` is a **devDependency** (#451). Importing it from anything the browser bundle reaches would ship a runtime dependency that isn't in `dependencies` — sanitise at ingest, store clean HTML in `src/data/`.
- **An intermittent test failure on this machine is CPU starvation, not a regression.** 55 suites, twenty-odd of them jsdom, oversubscribe a many-core box; the fix was measured and is already in place — `maxWorkers` capped at 5 in `vite.config.js`, `testTimeout`/`hookTimeout` at 30s, and Testing Library's separate `asyncUtilTimeout` at 10s in `src/test/setup.js` (pinned by `setup.test.js`). Re-run before believing a flake, and never weaken an assertion or add a bare wait to make one pass.
- **Browser e2e: `npm run test:e2e`** (Playwright; tests in `e2e/`, config `playwright.config.js`). Smoke tests for the layout/theming behaviour jsdom can't reach — the `light-dark()` theme repaint and the lazy class-data import + tree-render pipeline. Non-gating (`e2e.yml`, path-filtered, `workflow_dispatch`), like `links.yml`/`sources.yml`/`semgrep.yml`; deploys gate on `validate` only, never on e2e.
